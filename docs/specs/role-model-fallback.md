# Role / Judge 单备用模型故障切换

状态：设计已确认，尚未实施。经设计访谈 Q1–Q20 确认，其中 Q12 按用户修订、Q18–Q20 进一步明确。本文是目标行为合同，不表示当前 Runtime 已具备这些能力；不构成操作真实 Run、部署或发布的授权。

## 目标与范围（Q1–Q4 已确认）

- 为普通 Role Actor 与 Judge 各提供一个可选 Fallback Model Route，不包含 Manager 主会话。
- 显式配置备用路由即预授权：仅在确认模型调用故障且满足安全恢复条件时自动切换。未配置备用路由不自动选模。
- 每个角色最多一个备用路由，独立指定 provider、modelId 与可选 reasoningEffort，不支持备用链。
- GUI 修改只对新启动 Run 的 Definition Snapshot 生效；不追改在途 Run。当前 Run 的救援仍须显式运行期操作。
- 这是对旧设计排除模型 fallback 的受限扩展，不授权任意换模，也不修改业务图、验收条件或角色权限。

## 故障资格（Q5 已确认）

必须具有明确的模型请求失败证据，且宿主已终止该次请求的重试；不能仅凭耗时、idle、无提交结果或错误消息关键词推定模型已失效。

| 故障或结果 | 自动切换资格 |
| --- | --- |
| 明确的模型请求 5xx、429、网络连接故障、请求超时 | 满足安全恢复条件时可切换 |
| 认证/权限、额度耗尽、请求参数错误、上下文超限 | 不切换；按现有故障处理暂停 |
| 工具、存储、来源不明的错误 | 不切换；按现有故障处理暂停 |
| 用户取消 | 不触发切换，不改变现有取消语义 |
| Actor 未提交结果、Judge REJECT / NEED_CONTEXT | 本身不是切换依据，保留现有处理 |

模型可达性不是业务验收，备用模型仍须履行原节点合同与独立 Judge 流程。

## 安全恢复（Q6 已确认）

- 自动恢复是保留已完成事实、检查现场后续作，不是从头重放整节点。
- 旧执行必须已安全收口，恢复材料必须足以交代已发生操作。
- 用过工具不一律禁止恢复；但工具或后代任务仍在运行、存在无法核验的操作结果等情况必须保留 BLOCK。
- safe/idle/收口不证明外部副作用没有发生，不承诺外部操作恰好执行一次。
- 例：已执行 gh pr merge 后模型调用失败，备用 Actor 应先核验 PR 真实状态再继续，不直接重复合并。
- 已接受的 claim 或 judgment 不撤销、不重复提交或重判；故障切换不额外推进业务图。

## 生效期与宿主边界（Q7–Q8 已确认）

- 某角色切至备用路由后，当前 Run 的后续节点保持该备用路由；角色间状态独立，Judge 独立。
- 不自动探测或回切主模型，不修改 catalog。下一个新 Run 从原主路由开始。
- 第一版仅在宿主明确报告请求终止失败后介入，不增加 watchdog、不自动修改宿主 retry policy、不强行取消仍在重试的请求。
- 宿主 provider 若采用无限重试，插件可能收不到终止失败，不能保证及时 fallback。文档和配置界面必须披露此限制。

## 配置与 GUI（Q9–Q10 已确认）

- 允许省略显式主模型、继承 Run 冻结的 Manager 路由，同时单独配置备用路由。
- 备用模型省略 reasoningEffort 表示使用备用模型默认值，不继承主模型或 Manager 的档位。
- Role / Judge 编辑区区分“主模型”和“备用模型（可选）”，复用单路由选择控件；可配置、清除备用路由，清除即不再为新 Run 授权自动切换。
- 不增加故障码、重试次数等高级策略编辑器。
- 主备路由执行相同的启动前静态校验：确定误配阻断启动，包括确定误配的备用路由；元数据查询故障沿用现有注明未验证的处理。
- GUI 保存校验配置合法性；启动前检查已知路由误配。两者都不是消耗模型推理的健康测试，不能证明网络或额度可用。

## 恢复预算与人工路由（Q11、修订 Q12、Q18–Q20 已确认）

### 原始路由与恢复轮次

- A 始终是当前 Run 最初确定的主路由：显式 model 或启动时冻结的继承路由；B 始终是该 Run 冻结配置中的 fallbackModel。Manager 人工指定 C 不改写 A/B，运行中改 YAML 也不改变它们。
- 初始自动链为 A → B → BLOCK。配置 fallback 时，宿主对 A 的重试结束且故障符合资格后直接切 B，不叠加 Judge 原有的同主模型 fresh retry；B 终止失败则 BLOCK，不追加插件级自动重试或自动回主。
- 每次成功的 Manager 人工设置授权该角色新一轮有限恢复，链为 C → A → B → BLOCK；C 失败回 A 仍须遵守 Q5 的故障资格与 Q6 的安全要求。
- 即使 C 与 A 或 B 相同，也允许人工授权的新一轮按 C → A → B → BLOCK 重新尝试；该例外不放宽原始 A/B 必须不同的配置约束。
- C 正常时继续使用 C；C 合格故障回到 A 后，A 成功则继续使用 A，之后 A 再遇合格故障才切 B。不会自动返回 C，也不要求在一次 Turn 内走完整条链。
- 自动切换不能重置恢复预算；B 再失败则 BLOCK。仅 node_resume 不刷新自动切换预算，Manager 再显式设置模型才开启新一轮；重启同样不得刷新。
- 人工设置对 Role Actor 与 Judge 同规则；Judge 没有会话映射，授权从下一次判定派发生效，不替换正在进行的判定。相同三元件的人工设置只有在该角色已处于人工阶段（stage=manual、预算 0）时才算“无需变更”，否则同样按新一轮重置预算——C 与 A/B 相同、或与上一次设置相同，都不能静默丢掉授权。
- 在途派发的归因（#243）：人工设置在派发已发出、尚未结算期间不替换该派发；它随后以合格故障终局时，切换素材中的来源按“实际运行的路由”归因，写中性标注「人工路由未实派」，不把从未运行过的 C 写成失败来源。轮次结构不变——仍按离开人工阶段回 A、消耗本轮第 1 次切换，因此 A 可能被重派一次（A→A→B）；这是“不替换在途判定”的直接代价，由该标注如实披露。
- 在 C 或 A 阶段遇到不合格故障或不满足安全条件时，保留 BLOCK，不自动消耗后续路由继续尝试。
- 未配置 fallback 时不引入人工恢复链，保留现行行为，包括 Judge 已有的同模型重试一次。宿主请求级 retry policy 不变；本节不是整个多步任务的模型请求总数上限。

### 状态流示意

```text
初始：A ──合格故障且可安全恢复──> B ──终止失败──> BLOCK

人工设置：C ──合格故障且可安全恢复──> A ──合格故障且可安全恢复──> B ──终止失败──> BLOCK
```

每个位置成功时可以继续业务及后续节点；图中箭头不是从头重放任务的授权。取消、业务结论和非模型故障保留原有控制语义。

## 持久性与路由边界（Q13–Q15 已确认）

- 重启保留已激活路由、切换记录与预算、人工恢复状态，不因进程重启重置资格；仍遵守现行重启后暂停与显式恢复，不擅自执行业务。
- 主备的 provider + modelId 必须不同；仅 reasoningEffort 不同不构成备用模型。继承主模型时启动阶段以冻结主路由检查。
- 不同 provider 下相同 modelId 可以构成不同路由，但不保证上游故障隔离。
- 仅处理 Role Actor / Judge 执行当前派发任务时的模型请求失败；不自动接管 compact、会话物化、插件派发等维护阶段故障。

## 配置结构与可观察性（Q16–Q17 已确认）

- 配置采用 roles.<role>.fallbackModel / judgeRole.fallbackModel，与 model 平级，内部使用 provider、modelId 与可选 reasoningEffort。
- GUI 仅整理 Role / Judge 模型配置区域为“主模型 / 备用模型”两个分区；备用默认未配置，配置后说明自动切换语义及无限重试限制，不重做整个编辑器。
- 状态与持久事件展示角色、实际生效路由、来源（主 / 备 / 人工；在途派发未走过人工设置的路由时标为「人工路由未实派」）、切换原因，以及自动恢复预算的消耗状态。
- 成功切换主动通知 Manager，不再次等待批准；诊断脱敏，不保存凭据或完整请求载荷，不新建监控面板。

## 配置示例

```yaml
roles:
  developer:
    model:
      provider: primary-provider
      modelId: primary-model
    fallbackModel:
      provider: backup-provider
      modelId: backup-model
      # 可省略；省略使用备用模型默认档位，不继承主模型档位。
      reasoningEffort: high

judgeRole:
  # 可省略 model，沿用 Run 启动时冻结的主路由。
  fallbackModel:
    provider: backup-provider
    modelId: judge-backup-model
```

以上只展示模型字段，不是完整可运行 workflow；档位是否支持由实际模型元数据校验。

## 验收场景（由已确认规则推导，尚未执行）

| 场景 | 预期 |
| --- | --- |
| 主 A 的模型请求在宿主终止重试后报明确 503 / 429 / 网络故障 / 请求超时 | 旧执行安全收口且材料充分才切 B；不额外 fresh 重试 A |
| B 成功并进入该角色后续节点 | 保持 B，其他角色独立；新 Run 从原始 A 开始 |
| B 终止失败 | BLOCK，不自动回 A；node_resume、重启均不刷新切换预算 |
| 已切 B 后人工指定 C；C 合格故障 | 使用原始 A，A 再合格故障才转 B；B 再失败 BLOCK |
| 人工 C 恰好等于 A 或 B | 仍允许完整的人工新轮次，不因同路由跳过授权的 A/B 尝试 |
| C 或 A 报认证、权限、额度、参数、上下文、工具或来源不明错误 | 不切下一路由，保留原有 BLOCK；取消与业务结果不误触发 |
| 合并已成功，后续模型请求失败 | 不撤销事实，恢复材料充分时由新执行先核验真实 PR 状态再续作；不直接重做合并 |
| 子任务仍运行或无法核验外部操作结果 | 不自动重派，保留 BLOCK |
| 已接受 claim / judgment 后出现迟到错误 | 不撤销、不重复接受、不因错误再次推进业务图 |
| 派发在途期间人工设置 C，该派发随后合格故障 | 授权只对下一次派发生效；切换来源写「人工路由未实派」，不把未运行的 C 报成失败来源；轮次仍离开人工阶段回 A |
| 同一模型故障被多种生命周期通知重复观察 | 不重复切换、不重复消耗轮次、不产生并发恢复派发 |
| 宿主 provider 采用无限重试 | 不强行取消，不保证及时触发 fallback，GUI 与文档明确披露 |
| compact、会话物化或插件派发失败 | 保留原有故障恢复，不自动切模型 |
| 未配置 fallback 的旧配置或旧 Run 快照 | 不引入新自动切换，保留既有行为；不重写存量冻结配置 |
| 运行中修改 YAML | 当前 Run 的原始 A/B 不变，仅新 Run 使用新配置 |
| 主备仅 reasoningEffort 不同 | 拒绝；继承主路由时启动阶段完成同路由检查 |
| 备用确定误配或元数据查询异常 | 前者阻断启动；后者明确标注未验证，遵守既有静态检查策略 |
| GUI 配置、清除与重新加载 fallbackModel | 字段完整往返，不丢独立 effort，不改变主模型；清除备用只影响新 Run |
| 保存与运行状态展示 | 配置保存不宣称健康检查通过；状态/事件可区分主备及人工路由，记录脱敏且预算跨重启保留 |

实施时需在受控环境核验配置/schema、编辑器往返、运行链与安全恢复、持久性及回归行为；执行实际模型请求、真实 Run 或部署必须另获授权。未实施前不把以上验收场景写成已通过。

## 取舍与非目标

- 授权及恢复边界的理由见 [ADR-0004](../adr/0004-role-model-fallback-authorization.md)。
- 不支持 Manager 主会话自动换模、多备用链、自动探活回切、watchdog、宿主 retry policy 改写或完整请求载荷留存。
- 不承诺所有异常都不中断，也不承诺外部操作恰好执行一次；备用失败、证据不足或安全条件不满足时必须暂停。
- 本次交付设计文档，不自动进入实现、建票、部署或发布。
